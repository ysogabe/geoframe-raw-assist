# Core Image の白飛び（ハイライト）診断レポート（Issue #92、T3）

- 対象: `apple_default`・decoder 9・レンズ補正 ON（ADR 0002 の基本路線）の白飛びが、どの段で生まれ、どのレバーで戻せるか。
- 設計: [設計書](design/coreimage-highlight-diagnosis.md)（§10 の判定ロジック、§13 のオーナー判断はすべて推奨案で確定）。
- 道具: CLI 0.4.0（診断モード、`native/coreimage-cli/README.md`「診断モード」）、`scripts/compare_engines.py --diagnosis`（T2）。
- 計測: 2026-10-21、macOS 27.0.1 / Apple M3、rawpy 0.27.0 / LibRaw 0.22.1、Python 3.14.6。10 カット preview（2400px）+ 3 カット full、エラー 0 件。
  帰属（§3）・ROI（§6.3）は計測 3 回目（`diagnosis2`、§8 の 3〜5 を反映）の値。段階・掃引・タスク C の合否は 2 回目と同一（§1）。
- 表記: **【事実】** = 計測・コード・公開 API の挙動で確認したこと（条件を併記）。**【推測】** = 未検証の見立て。
- 画像・float dump はコミットしない。本文には数値・表・パスだけを置く。位置情報・撮影地は書かない。

## 0. 要点

| 論点 | 結論 |
|---|---|
| 白飛びはどこで生まれるか | **線形段（S1）で表示白 1.0 を超えた画素が、トーン段（S2）で 1.0 に固定され、色域マッピング（S3）で 1.0 に切られる**。S1 で 1.0 超の画素率 ≒ S2 ≒ S3 ≒ 16bit ≒ 8bit（10 カット中央値で差 ≤ 0.6pt）。色域マッピング・16bit・P3/sRGB は新しい白をほぼ生まない【事実】 |
| センサーが情報を持たない割合 | CFA 飽和（2×2 セル、`white_level − 32`）は 10 カット中央値 1.8%（0.0〜20.1%）。CI の 8bit 白飛び 13.0% の大半はセンサー飽和ではなく、WB ゲイン × baselineExposure（+0.4EV）で表示白を超えた**デコーダ/トーン**に帰属する【事実】 |
| 帰属（§10.1） | K を S3 dump（8bit で 255 に丸まる値）から取り、`cloud_grad` に低彩度の条件を足した計測 3 回目で、`sky_bright` / `cloud_grad`（preview 10 カット × 2）の分類: デコーダ/トーン 11、混合 4、センサー 2、クリップなし 3、検証不能 0。シーン判定（preview）: デコーダ/トーン 6、混合 4、**検証不能 0**（DSC04754 は `cloud_grad` が空に移ってデコーダ/トーン、§6.3）。「8bit 量子化」が最大で分類される ROI は無い【事実】 |
| 「8bit 量子化」「JPEG 符号化」の中身 | 規則 3「8bit 量子化（白の手前 1/255）」（旧「色域・SDR 出力」）は S2 が [0, 1] で S3 が 8bit で 255 に丸まる画素。旧「検証不能」は S3 ≥ 0.98 の「JPEG 符号化」と、それ未満の「検証不能」に分けた（§3.3）。K を 8bit JPEG から取った参考の内訳（13 件）では、**真に説明できない画素（S3 < 0.98）は各 ROI の K の 2.7% 以下**で、残りはすべて白の手前 0.02 以内の丸めと JPEG。色域・色空間の損失ではない。K を S3 から取る本計測では JPEG 符号化・検証不能は構造上 0【事実】 |
| タスク C | 計測 1 回目の C1（brightness 1.1）と C3（線形座標の CIToneCurve）は候補の値の誤りで不合格だった。原因を確かめて値を直し、再計測した（§4）。**C1'（`exposure` −0.7 + `shadow_lift` 40 + brightness 1.0）が、CI 自身の明るさを基準にすれば preview 10/10 カットで自動判定 (1)〜(5) を満たす**。カメラ JPEG を基準にすると 5/10。full は 3 カット中 1 が原寸の magenta_rate で不合格（§5.1）【事実】 |
| **判定（§10.3）** | **A（CI 継続）。オーナー判断（2026-10-21）で確定**: 合否の基準を `d_base`（CI 既定）比に較正し（§13 判断 5）、C1'（−0.7）が「デコーダ/トーン」「混合」10 カットすべて（preview 10/10）で自動判定 (1)〜(5) を満たした。目視 (6) はオーナーが確認して「Core Image の候補で問題なし」と判断した。B の条件（検証不能 2 カット以上）は満たさない（検証不能 0）。経緯: 設計書どおりカメラ JPEG 基準で厳格に読むと 10 カット中 6 で C（未判定）だった。差を決めていたのは候補ではなく、カメラ JPEG の DRO（中間調・暗部の持ち上げ）と CI 既定の差（DSC04705 / 04754 / 04462 は `d_base` 自体がカメラ比 −0.15 / −0.13 / −0.05）（§5.2、§8） |
| #81 への引き渡し | C1' の値（§7）。2026-10-21 に #81 へ引き継いだ（§8）。`brightness` > 1 は後段がガンマ空間の乗算のため白側を戻してしまう（使わない）。`CIToneCurve` の制御点は sRGB ガンマ座標（§4.3）。C3（gamut OFF）は偽色（magenta_rate 0.026〜0.067）が出るので本番候補から外す |

- 【事実】**白の率は S1 で決まる**。S1→S2 の新規損失（S1 で [0,1) だった画素が S2 で白）は中央値 0.2pt（最大 2.1pt、DSC04532）、S2→S3 は全カット 0（gamut マッピングは 1.0 超の画素を 1.0 に切るだけで、[0,1] の画素を新たに白にしない）、
  S3→S4（lens ON/OFF の幾何差があるため率の差で代用）は ±0.3pt、S4→S5（16bit → 8bit JPEG）は 0.3〜3.0pt（白の手前 1/255 以内の画素が 255 に丸まる分 + JPEG）。
- 【事実】S1 の 1.0 は baselineExposure（ファイル値 0.4EV、×1.32）込みの表示白で、`exposure` / `baselineExposure` は `linearSpaceFilter` の前に掛かる（設計書 §2.4、CLI 0.4.0 のスモークで `baseline 0 ≡ exposure −0.4` を確認）。
  8bit 出力で B だけが白の画素（`blue_only_clip`）は 10 カット中央値 7.6%（DSC04705 24.5%）で、S1 でも B の 1.0 超率が R / G より高い（DSC04473: B 8.1% / G 0.4% / R 0.04%）。青空で B が先に飛ぶ機構は設計書 §2.3 の算術（WB B ×1.70 × 1.32）のとおり。
- 【事実】EDR（0.5 / 1 / 2）は 8bit 白を 16.5 / 18.0 / 20.5% に増やし、boost 0 / 0.25 / 0.5 / 0.75 は 10.9 / 11.1 / 11.3 / 11.8%（既定 13.0%）、`exposure` −0.3 / −0.7 / −1.0 / −1.5 は 8.7 / 3.6 / 2.2 / 0.05%（§13 と同じ傾向）。
  gamut OFF（jpeg）は 13.0% で既定と同じ（1.0 超は JPEG 化で切られる）。tiff16 sRGB と Display P3 の白は同率（8.1% の blue_only、P3 は sRGB へ変換してから数えた）。
- 【事実】`d_lens_off` と `d_base` の全画面 clip8 差は preview で ≤ 0.27pt（§7.3 の前提 0.5pt 以内）。full では 1.2 / 0.5 / 5.5pt（DSC04473 / 04607 / 04705）で前提を超えるが、
  これは lens OFF の原寸 JPEG で白の手前の画素が 254 に落ちる計測上の問題（§6.4）であり、現像の差ではない。

### 4.3 CIToneCurve の色空間と C3 の曲線（T2 の未解決点 8）

- 【事実】計測 1 回目の C3（線形座標で制御点を置いた `CIToneCurve`）は、中間調がカメラ比 +0.19〜+0.42（中央値 +0.33）明るかった。

## 6. API の境界と計測の限界

### 6.1 公開 API で制御できること【事実】

- 白の位置を動かす: `CIRAWFilter.exposure`（`linearSpaceFilter` の前、1:1 EV）、`baselineExposure`（同じ効き。上書き可だが `exposure` と冗長）、`boostAmount`（1.0 を固定点にした大域的なトーン。白飛び率は 13.0 → 10.9% までしか下がらない）。
- 1.0 超を残す: `isGamutMappingEnabled = false` で `outputImage` の 1.0 超（最大 2.7）が float で読める。`CIToneCurve` / `CIHighlightShadowAdjust` / `CIExposureAdjust` を `outputImage` の後に挿せる（`CIToneCurve` の座標系は §4.3）。
- 読み戻し: `applied` の実効値（`baseline_exposure` 0.4、`boost` 1.0、`boost_shadow` 0.9、EDR 0、gamut true が 10 カット共通）。
- 観測: S1（boost 0 + gamut OFF）、S2（gamut OFF）、S3（既定）の float dump、`linearSpaceFilter` の定数置換による応答関数の標本化。

### 6.2 公開 API で制御・観測できないこと【事実】

- デモザイク・NR・ハイライト再構成の中間画像、トーン曲線の式、gamut マッピングの方式。**CFA が飽和した画素を CI がどう埋めたか**（S1 に値はあるが再構成値か実測値かは区別できない）。
- boost の曲線に「ニー」（1.0 手前からの圧縮）を入れる手段。boost 1 は 1.0 を固定点にして 1.0 超を傾き ≈0.14 で圧縮するだけで、gamut ON がそれを 1.0 で切る。既定の経路で白の手前の階調を残すレバーは `exposure` 以外に無い。
- `extendedDynamicRangeAmount` は 1.0 → 1.25 / 1.5 に押し上げる（SDR では白飛びを増やす）。
- `CIHighlightShadowAdjust` の式（局所適応・半径の意味）。線形作業空間で掛かる。
- gamut マッピングは in-range の画素をほぼ動かさない（平均 1e-4〜2e-3）が、**高彩度の画素では最大 0.14〜0.20 動く**（DSC04754 の ΔE76 0.18、DSC04473 full の最大差 0.20）。設計書 §2.2 の「実質 clamp」は無彩色〜低彩度に限る。

### 6.3 ROI 抽出の限界【事実（目視）】

- 計測 2 回目まで、DSC04754 の `cloud_grad` は雲ではなく手前の明るい被写体（青い車体。帯 0.6 < L < 0.98 に 70% 以上入り、起伏が最大の箱）に落ちていた。
  計測 3 回目で帯に HSV の S < 0.2 を足し（`CLOUD_GRAD_MAX_SAT`）、**`cloud_grad` は右上の曇天の空（ミラーの横）に移った**（`sheets/DSC04754_preview_rois.jpg` を目視。箱の端にミラーの縁と遠景の稜線が少し入る）。
  分類はデコーダ/トーン（0.86）、シーン判定もデコーダ/トーンになり「検証不能」は消えた。同カットの `sky_bright` は K が 0.0%（JPEG では 0.2%）で「クリップなし」のまま。
- 夜明けの桃色の雲（DSC04532、箱の帯内の S は p50 0.08 / p90 0.10 / p99 0.12）の `cloud_grad` は計測 2 回目と同じ箱（[1080, 600, 1320, 840]）で、指標も同一（目視でも同じ位置）。
- S < 0.2 で `cloud_grad` が動いたのは DSC04754 のほか 3 カット: DSC04607（[2160, 240] → [1920, 240]、preview / full）、DSC04579（[1440, 360] → [1920, 360]）、DSC04746（[840, 480] → [1080, 480]）。
  いずれも元の箱の帯内に S 0.19〜0.25 の画素（青みの遠景の稜線・空）が p90 で入っていた箱で、隣の低彩度の空・雲に 1 箱ずれた（目視で雲・空の上にあることを確認）。閾値 0.25 なら DSC04754 だけが動くが、オーナー判断の 0.2 を採った。
  条件を満たす箱が無いカットは 13 件中 0（その場合は従来の帯で選び直し、`diagnosis_summary.json` の `roi_info.cloud_grad_low_sat` が false になる）。
- 室内 2 カット（DSC04432 / 04462）の `sky_bright` / `cloud_grad` は窓。センサー飽和（46% / 97%）は本物。
- `d_lens_off` の ROI 位置合わせは preview で全件成功（応答 ≥ 0.08）だが、lens OFF は幾何が違うので ROI 単位の lens ON/OFF の clip 差が最大 4.7pt（DSC04532 `sky_bright`）。帰属は lens OFF 幾何だけで閉じているので結論には影響しない。

### 6.4 計測上の問題（ハーネス側。結論には影響しない範囲）【事実】

- **K を 8bit JPEG から取ると、lens OFF で白を数え損なう**（計測 3 回目で修正済み）: DSC04705 full の `d_lens_off` は clip8 0.332 に対し S3 dump の ≥1 は 0.385、`d_base`（lens ON）0.387。`sky_bright` の 8bit ヒストグラムで 254 が 23.8k 画素（lens ON 7.0k）。
  周辺減光補正が無い lens OFF では空の値が 1.0 付近に留まり、JPEG（q 0.92）の量子化で 255 → 254 に落ちる。**preview でも起きていた**（DSC04473 `sky_bright` の箱で 255 が 35.2k、254 が 20.5k 画素）。
  計測 3 回目は K を S3 dump の ≥ 0.9955（8bit sRGB で 255 に丸まる値、lens OFF 幾何）から取った。全画面の K は DSC04705 full 0.332 → 0.391（`d_base` 0.387 に一致）、DSC04473 full 0.084 → 0.102、DSC04607 full 0.068 → 0.072。
  lens OFF の tiff16 は現像していない（`d_tiff_srgb` は lens ON で幾何が違う）ので使わなかった。dump が無いときは従来の JPEG の K に戻り、`k_source` が `jpeg8` になる（そのときは帰属が全部「検証不能」になるので、効くのは K/ROI だけ）。
  【推測】S2 > 1.0（S3 = 1.0）の画素まで JPEG で 254 以下になるのは、B だけが白の画素（青空）で 4:2:0 の色差の間引きが B を下げるため。
- `stage_loss_s4s5`（0.3〜3.0pt）には 8bit 丸めと JPEG の両方が入る。tiff16 → jpeg の寄与を分けるなら jpeg を可逆（png）で出す 1 本が要る。
- 計測 1 回目の `curve_global False` は曲線の標本数の問題（§4.1）。`TONE_CURVE_BOOST1` を 24 点に置き換えた。
