# 合成結果の共通selector（#5 F1）報告

状態: 親の統合worktreeで全145テスト、型検査、lint、Viteビルドを確認済み。
専用IDのQAアプリで実WKWebViewのGUI検収を完了（2026-10-24）。下記参照。

## 原因

画面に出す合成は`App.tsx`で選択・プリセット・調整と照合していた一方、写真対象（`viewingCaptureOf`）は
生の本合成を優先していた。古い本合成[1,2]と新しいプレビュー[2,3]が並ぶと、画面は[2,3]、
SELECTED PHOTO/EXIF/写真採用先は1を指した。

## 変更

- `app-state.ts`: `isMergeResultCurrent` / `currentMergeResultsOf`を追加。フレーム集合・プリセット・調整値の全量が
  今の設定と一致する結果だけを`full` / `preview` / `shown`（本合成優先）として返す。
- `viewingCaptureOf`は`shown`の先頭を使い、合う結果が無ければ今の選択の先頭フレームへ戻る。
- `App.tsx`は表示用の結果と合成採用ボタンを同じselectorから得る。`OperationPanel`の重複した照合は削除。
- 合成タイルの採用ボタンの対象（`mergedAcceptTargetOf`）は **今の設定に合う本合成だけ**。合わなくなった本合成は、
  未採用なら新規採用できず、採用済みでもこのボタンの宛先にしない。
- 採用済みの合成は`acceptedMergeOf`で別に引く（先頭フレーム・成果物・`isCurrent`）。`isCurrent`が真のとき
  だけ✓を今の合成に付け、偽のときは「採用済み（以前の設定、N枚）」を別タイルと合成パネルの行に出す。
  そこから原寸ビューアで確認でき、専用ボタンで採用を外せる。今のプレビューへ旧本合成の✓は移さない。
  成果物を引けない採用は「成果物なし」と表示し、取り消しだけできる（複数あれば1件ずつ順に取り消す）。
- `accept/merged`のreducer: 既採用と完全一致する取り消しは常に最初に通す。**新規採用は選択中グループの
  「今の設定に合う本合成」で、先頭フレームが一致するときだけ**許可する（プレビュー・合わなくなった本合成・
  非選択グループはactionを直接渡しても拒否）。
- `mergedResultFor`（書き出し・一覧の枚数）は従来のまま。ただし「スナップショット」とは **完全な不変の成果物
  ストアではなく、グループの現在保存されている本合成を先頭フレームで引く既存仕様**を指す。同じ先頭フレームで
  本合成をやり直すと、採用は新しい本合成を指す（この置換は今回の範囲外）。
- `isMergeResultCurrent`は、結果のadjustmentsがnull/undefined/不正な形でも落ちず「合わない」扱いにする。
- `screen/operation`は、復帰先グループの現在のフレーム集合に合う保存済み結果（本合成優先、無ければプレビュー）
  のプリセットと完全なadjustmentsを操作値へ復元する（overridesはプリセット既定との差分だけ）。9キーが
  揃わない・プリセットが一覧に無いlegacyな結果は復元せず、従来どおり推薦プリセットから始める。
  グループごとの設定mapは持たず、結果をcurrent扱いにするのではなく、復元した操作値が共通selectorを満たす。
- グループ移動の確認（`adjustmentsLostOnLeave`）は、復元できる保存結果があるグループでは「戻ったときに実際に
  復元される値（復元するpreset + overridesの全9値）」と今の値を比べる。復元したままなら確認しない。手動変更や
  既定へのresetは、戻ると保存recipeに変わるので確認する。同じフレームの本合成Aと現在のプレビューBがあれば、
  戻るとA（本合成優先）になるのでBは失われる扱い。プリセット名だけの違いは値が同じなら失われない。復元できる
  結果が無いグループは従来の`changedAdjustmentKeys`基準。`changedAdjustmentKeys`自体（表示・リセット用）は変えない。
- 比較エリアに合成を出すのは表示面（`effectiveViewingOf`）がmergedのときだけ（`comparisonSurfaceOf`）。
  写真を見ている間は、写真が未現像でも合成へ黙って切り替えない。
- 選択中でないグループ（一覧カードの代表写真）はプリセット・調整が不明なので、フレーム集合だけで照合する。
- `BracketMerge.tsx`の案内を、合成の実挙動（`exposure` / `highlight_recovery`は無視、他は反映。
  `Merge.swift`の`ignored`と一致）に合わせて訂正。

## 注意点

- 照合は調整値の全量なので、合成が無視する露出・ハイライト回復を動かしても結果は「合わない」扱いになる
  （指示どおりの保守的な挙動）。無視キーを照合から外すかは別判断。
- 「合う結果なし」の間は、合成を見ていても対象は今の選択の先頭フレームになる（`effectiveViewingOf`が写真面として扱う）。
- 照合は`===`の完全一致。Rustは調整値を契約の値域へクランプして返すが、UIが作る値（スライダーは同じ範囲・
  候補はRust側で同範囲にクランプ済み・プリセット既定は正規化済み）は範囲内なので、クランプ前後で食い違う
  具体的な経路は確認できていない。範囲外の値が入る経路が見つかったら、比較側ではなく入力側で正規化する。


## 親の実画面検収

専用5ペア/3グループで、contrast 1.10の3枚本合成→採用→他グループ往復を確認した。recipeとcurrent/採用状態が復元され、復元値を触らなければ次の移動で破棄確認は出なかった。手動変更が失われる場合の確認は維持されている。

旧3枚の採用を残して先頭DSC04513を外し、DSC04514/04515の新2枚previewを作ると、表示lead/SELECTED PHOTO/EXIFは04514で一致した。新previewには✓が付かず、旧3枚は以前の設定の別タイルに残り、原寸表示と取消ができた。長いタグは2行で収まり、隣の写真タイルを覆わなかった。

未現像04515を選ぶとその写真が表示され、合成へ暗黙に切り替わらない。採用済みartifactのgroup+lead識別は既存仕様のままで、同lead再合成の置換を解決したとはしない。実AEB画質の受入試験ではない。
