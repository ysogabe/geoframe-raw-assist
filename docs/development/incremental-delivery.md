# 分割作業の逐次統合と後片付け

2026-10-25のオーナー指示。分割したブランチ・worktree・PRは親が検収、マージ、同期、掃除まで担当する。通常のマージと掃除は継続承認済みで、都度の確認は求めない。

## 作業の閉じ方

1. 独立して検証できる最小単位に分け、担当・受入条件・依存先を決める。原則、統合待ちの変更は1本にする。独立した調査や実装だけを並行する。
2. 専用worktreeで実装し、親が差分と必要なテスト・実CLI・実画面を検収する。レビュー指摘を解決し、検証したHEADと条件を記録する。
3. PRの最新HEAD、レビュー、チェック、競合を確認し、既定ブランチへマージする。依存する実装は更新済みの既定ブランチから始める。スタックが必要なら短く保ち、下から逐次解消する。
4. マージ後のツリーが検証済みの変更と一致することを確認し、既定ブランチを同期する。後続PRが参照するbaseを更新してから、不要になった作業ブランチとworktreeを片付ける。
5. 未完了のPRを残すときは、具体的な阻害条件と次の確認を記録する。単なる「最後にまとめて確認する」を理由に残さない。

## 再検証の範囲

コード・依存・ビルド設定・関連環境が同じなら、履歴や文書が変わっただけで全テストを繰り返さない。既存の検証記録とマージ後のツリー比較を使う。競合解消や実装変更、新しい組合せが生じたときは影響する検証を行い、共有部分へ広く影響するときに全体検証する。

機能の検収と配布形の検収は別に記録する。配布形の未確認をすべての独立した評価経路の保留理由にはしない。一方、未確認の動作や素材待ちは合格扱いにせず、担当するIssueと検証条件を残す。

## 掃除の条件

統合確認済みで、進行中の作業や他のPRが使っていないものだけを対象にする。未コミットのユーザー作業、元写真、設定、採用結果は触らない。必要な計測結果・凍結物・配布物は削除前に保管先とハッシュを確かめる。再利用するビルド環境や未完了の検証用worktreeを残す場合も、理由と責任者を明記する。

重大な問題、所有者不明の変更、実際の自動承認レビュー拒否があれば、その範囲の操作を止めて報告する。通常の後片付けをユーザーへ差し戻さない。

個人共通指示にも同じ方針を記録し、リポジトリをまたいで適用する。
