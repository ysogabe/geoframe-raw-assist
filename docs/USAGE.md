# GeoFrame RAW Assist — 使い方

ソースからビルドして起動し、写真を現像して書き出すまでの手順です。アプリの紹介は [README](../README.md)、内部の仕組みは [技術設計](DESIGN.md) を参照してください。

## 1. 用意するもの

- macOS。最小の対応は 14.0 ですが、動作を確認しているのは macOS 27.0.1 / Apple M3 だけです。
- Xcode（Swift 5.9 以上。Core Image の現像 CLI のビルドに使います。検証は Swift 6.4）。
- Rust（`src-tauri/Cargo.toml` の `rust-version` は 1.77.2）。
- Node.js 22.13 以上（`package.json` の `engines`）。
- 現像したい Sony α の JPEG+ARW 同名ペア。アプリにサンプル写真は同梱していません。

評価用の Python スクリプトを動かすときだけ、Python 3 が要ります（[7. 開発者向け](#7-開発者向け)）。アプリ本体に Python は要りません。

## 2. ビルドして起動する

```bash
npm install
env -u CI npm run tauri:dev      # 開発用に起動
env -u CI npm run tauri:build    # 配布形（.app と DMG）をビルド
```

`tauri:dev` と `tauri:build` は、先に `npm run build:coreimage` を自動で実行します。これは Swift の現像 CLI `geoframe-ci-develop` をビルドして `src-tauri/binaries/` に置く手順です。`cargo build` や `cargo test` を単独で回すときは、一度手動で実行してください。

```bash
npm run build:coreimage
```

環境変数 `CI=1` が設定されている環境では、そのままだと tauri CLI が `--ci 1` を受け付けずエラーになります。そのため上のコマンドはすべて `env -u CI` を付けて `CI` を外しています。

ビルドした `.app` は次の場所に作られます。

```bash
open "src-tauri/target/release/bundle/macos/GeoFrame RAW Assist.app"
```

ブラウザで `npm run dev`（vite 単体）を開いても動きません。画面は Tauri の WebView 上でだけ動きます（ファイル操作や現像を Tauri コマンドで行うため）。

### DMG の作成が失敗したとき

DMG の作成（`bundle_dmg.sh`）がまれに失敗することがあります（2026-10-20 時点で 3 回連続成功し、再現していません。Issue #76）。失敗したときは、作りかけのイメージ `src-tauri/target/release/bundle/macos/rw.*.dmg` を消してから再実行してください。

`.app` だけが必要なら、DMG を作らずにビルドできます。

```bash
env -u CI npm run tauri:build -- --bundles app
```

### 署名について

配布用の Developer ID 署名と公証はしていません（`tauri.conf.json` に署名設定はありません）。自分でビルドした `.app` を、そのビルドした Mac で使う想定です。

## 3. 写真の置き場所

対象は **JPEG と ARW の同名ペア**です。Sony α の既定の命名（`DSC02943.JPG` と `DSC02943.ARW`、`DSC` + 数字 5 桁）だけを対象にします。拡張子の大文字小文字は問いません。1 つのフォルダの直下に置いてください。サブフォルダは見ません。

```
<選んだフォルダ>/
├── DSC02943.JPG
├── DSC02943.ARW
├── DSC02944.JPG
└── DSC02944.ARW
```

初めて起動すると「まず現像元フォルダを選んでください」と表示されます。「フォルダを選ぶ」を押すと macOS のフォルダ選択ダイアログが開きます。選んだフォルダはアプリのデータフォルダの `config.json` に保存され、次回の起動でも使われます。あとから変えるときは、画面左のサイドバー「現像対象フォルダ」の「フォルダを選ぶ」を使います（解析の実行中は変更できません）。

フォルダを選ぶまでは、解析・現像・書き出し・候補生成が `SOURCE_ROOT_NOT_CONFIGURED`（現像元フォルダが未設定）で止まります。

`~/Pictures` や `~/Desktop`、SD カードなどの外部ボリュームを選ぶと、macOS が初回にアクセス許可を求めます。許可しないと読み取れず、画面には「写真が 0 枚」ではなく許可を促すメッセージが出ます。「システム設定 > プライバシーとセキュリティ」で許可してから、フォルダを選び直してください。

撮影 ID（`DSC` の連番）はカメラが付けるため、SD カードが違うと別の写真に同じ ID が付くことがあります。そのため、解析・現像・サムネイルのキャッシュはフォルダごとに分かれています。前に使ったフォルダに戻すと、そのフォルダの解析と現像の結果をそのまま再利用します。

## 4. 操作の流れ

どの操作でも、元の JPG と ARW は変更しません。生成物は次の保存先に置かれます。

保存先は、macOS では `~/Library/Application Support/com.geoframe.rawassist/`（以下 `$APPDATA`）です。リポジトリの中には何も書きません。

```
$APPDATA/
├── config.json                          アプリ設定（現像対象フォルダ）
├── analysis/<folder>.json               解析結果（グループ・スコア・推薦）のキャッシュ
├── thumbnails/<folder>-<ID>.jpg         一覧表示用サムネイル（長辺 640）
├── coreimage/
│   ├── preview/<ID>_<hash>.jpg|.json    プレビュー現像（長辺 2400）と来歴
│   ├── full/<ID>_<hash>.jpg|.json       本現像（原寸）と来歴
│   ├── merged/<先頭ID>-merged<枚数>-<preset>-<hash>.jpg|.json   ブラケット合成（原寸・書き出し可）
│   ├── merged_preview/ （同名）          ブラケット合成のプレビュー（長辺 2400・書き出し不可）
│   └── candidates/                      候補生成の一時ファイル（終了時に削除）
└── export/<バッチ名>/
    ├── <現像ファイル名>.jpg
    └── manifest.json                    書き出し内容とレシピの記録
```

`<hash>` は調整値・プリセット・CLI の版・元の ARW などから決まる識別子で、同じ条件で再実行するとキャッシュが再利用されます。`<folder>` は現像元フォルダを識別する 8 桁で、別のフォルダの同じ撮影 ID が混ざらないようにするためのものです。命名とキャッシュキーの詳細は [API 契約](API_CONTRACT.md) §4 を参照してください。

### 4.1 解析

フォルダを選ぶと、解析が始まります（「解析を開始」で始める場合もあります）。現像対象フォルダの JPEG から EXIF を読み、シャープさ・白飛び・黒つぶれなどを採点し、サムネイルを作って、撮影グループにまとめます。進捗は画面に出ます。

結果は `analysis/<folder>.json` にキャッシュされ、2 回目以降は即座に表示されます。やり直したいときは、画面上部の再解析ボタンを使います。

### 4.2 選別

グループごとに、代表カットと推薦の理由（シャープさ、白飛びの少なさ）が表示されます。あわせて、RAW 現像の推薦レベル（強く推奨／推奨／検討／JPEG で十分）と、その理由が出ます。代表は手動で変更できます。

グループの種類は「連写」「ブラケット」「類似」「単写」です。操作パネルでは、元の JPG の確認、フィルムストリップ、原寸ビューア、矢印キー（←→）での前後のグループへの移動ができます。

仕上げる写真は「この写真を採用する」で採用にします。採用した写真が書き出しの対象になります。

### 4.3 現像

操作パネルで現像プリセットを選び、スライダーで調整します。スライダーを動かしても自動では現像されません。

1. 「プレビュー現像」で結果を確かめます（長辺 2400px）。
2. 良ければ「本現像」で原寸の JPEG を作ります。カメラの JPEG の EXIF を引き継ぎます。

現像前後の比較も画面でできます。調整値を捨てるとき（別の写真やグループへ移るときなど）は、確認ダイアログが出ます。プリセットの表は [5. 現像プリセット](#5-現像プリセット) にあります。

処理時間の目安は、macOS 27.0.1 / M3 で ISO 6400 の 1 カットを Core Image CLI 単体で処理した場合に、プレビューが約 1.0 秒（RSS 約 170MB）、原寸が約 2.0 秒（RSS 約 270MB）です（[回帰確認手順](development/coreimage-regression-check.md) §1）。アプリ全体では、画面の案内に「プレビューは約 1〜3 秒、本現像は約 5〜20 秒」とあります。

本現像と合成は、完了まで画面で待ちます。途中でキャンセルはできません。

### 4.4 ブラケット合成

露出を変えて連続撮影したカット（AEB）は、解析で「ブラケット」として検出されます。操作パネルの「ブラケット合成」で使うフレームを選び、合成します。

- 方式は Exposure Fusion（Mertens）です。各フレームの「よく撮れている部分」を重み付けして直接 1 枚にするので、HDR のトーンマッピング特有の不自然さが出ません。合成は Core Image CLI の 1 リクエストで行います（位置合わせ MTB + Mertens）。
- 合成用のデコードは、フレームごとの明るさ正規化をしません。正規化すると露出差が消えて、合成する意味がなくなるためです。プリセットのトーン調整は合成後に 1 回だけかかります。
- 手持ちのズレは、合成前に位置合わせします（結果に「位置合わせ済み」と表示されます）。
- 枚数は **2〜9 枚**です。1 つのグループに別シーンのブラケットが混ざることがあるため、フレームの選択は手動です。既定では先頭から最大 9 枚を選んであるので、露出補正と平均輝度が階段状に並ぶ、ひと続きのフレームだけを残してください。
- 「合成プレビュー」（長辺 2400px）で確かめてから「ブラケット合成」で原寸の本合成をします。書き出しに使えるのは本合成の結果だけです。
- 実際の AEB や三脚での長秒ブラケットでの画質は、まだ確認できていません（[ブラケット Rust 移植の報告](reports/coreimage-bracket-rust-report.md)）。

### 4.5 現像候補の自動生成

現像パネルの「自動候補を作る」は、ARW を縮小デコードした代理画像（長辺 640px）で調整値を探索し、候補を示します。ペアの ARW が必須です。

- 候補は「自然」（プリセット値そのもの。他の候補の比較基準）、「星空」（長秒・低 EV100 の EXIF で、点光源が多数ある写真のみ）、「前景を明るく」、「低ノイズ」、「SNS 向け」です。表示された指標と理由を見て、人が選びます。
- 選んだあと、必要ならスライダーで調整してから「プレビュー現像」または「本現像」を実行してください。候補を選んだだけで、現像が勝手に始まることはありません。
- 露出はプリセット値と ±0.5EV の 3 格子で探索します。`highlight_recovery` と `wb_temp` は探索せず、プリセット値のままです。
- 基準より白飛び・黒つぶれが大きく悪化する候補などは返さず、応答の `rejected` に理由を残します（画面では「出なかった候補」）。
- 代理画像での評価なので、美的な正解や最終的な RAW 品質を保証するものではありません。

探索の空間・安全判定・実測は [PSO 移植の報告](reports/coreimage-pso-loop-report.md) を参照してください。

### 4.6 書き出し

画面上部の「書き出しへ」を開き、採用した写真ごとに書き出す形式（カメラ JPG／現像済み。ブラケットは本合成の結果）を選び、バッチ名を付けて「書き出し」を押します。バッチ名は半角英数字・ハイフン・アンダースコアが使えます（それ以外の文字は `_` に置き換わります）。

選んだ写真は `$APPDATA/export/<バッチ名>/` に JPEG のまま複製（再エンコードなし）され、書き出し内容とレシピを記録した `manifest.json` が書かれます。「Finder で表示」で書き出し先を開けます。同じバッチ名で再度書き出すと、以前の現像 JPEG がフォルダに残ったままになります。

### 4.7 Apple 写真への登録

書き出したあとの「Apple フォトへ登録」で、書き出したバッチを「写真」アプリのアルバム `GeoFrame RAW Assist <バッチ名>` に取り込みます（同名のアルバムが無ければ作成します）。

初回だけ、macOS の自動化の許可ダイアログ（実行元のアプリが「写真」を操作しようとしています）が出ます。「OK」を選ぶと登録が進みます。許可しなかった場合は、「システム設定 > プライバシーとセキュリティ > オートメーション」を開き、実行元のアプリの下にある「写真」をオンにして、もう一度実行してください。実行元は、ビルドした `.app` なら GeoFrame RAW Assist、`tauri:dev` ならターミナルなどです。許可するまでは写真は登録されず、画面にエラーが出ます。

## 5. 現像プリセット

| name | 表示名 | 用途 |
|---|---|---|
| `neutral_recovery` | 階調回復 | 自然な明暗差を保つ標準仕上げ |
| `landscape_clear` | 風景クリア | 遠景の輪郭と色をくっきりさせる |
| `nightscape` | 夜景ノイズ低減 | 高ISO夜景のノイズを抑え暗部を持ち上げる |
| `sunset_glow` | 夕景・マジックアワー | 夕焼けの暖色を強め空の階調を守る |
| `indoor_warm` | 室内・料理 | 室内照明の暖かさを残し料理を明るく見せる |
| `portrait_soft` | 人物・柔らか | 肌を滑らかに見せる柔らかいコントラスト |
| `monochrome_street` | モノクロ | 彩度を落としコントラストで見せる白黒仕上げ |
| `highlight_rescue` | 白飛び救済 | 飛びかけた空や光源の階調を最大限引き戻す |
| `shadow_rescue` | 黒つぶれ救済 | つぶれた暗部を大きく持ち上げ、増えるノイズを抑える |
| `backlit_rescue` | 逆光 | 明るい背景の階調を残しつつ、影になった被写体を持ち上げる |
| `vivid_travel` | ビビッド | 旅の記録向けに色を鮮やかに強調する |

各プリセットは、露出・色温度・シャドウ持ち上げ・ハイライト回復・明るさ・コントラスト・彩度・シャープネス・ノイズ低減の 9 項目の初期値です。値の正は `src-tauri/src/presets.rs` で、Core Image の `apple_default` を基準に再調整済みです（[再調整レポート](reports/coreimage-preset-retune-report.md)。値の一覧は [API 契約](API_CONTRACT.md) §5）。

写真を開いたときの初期プリセットは、解析の推薦理由に合わせて選ばれます（黒つぶれ→黒つぶれ救済、白飛び→白飛び救済、両方→逆光、高 ISO・夜景→夜景ノイズ低減）。画面のスライダーで上書きでき、調整値ごとに別のファイルとして保存されます。

## 6. うまくいかないとき

エラーは、`SIDECAR_*` のような code がそのまま画面に出ます。code の意味と出るコマンドは [API 契約](API_CONTRACT.md) §0.5 の一覧にあります。

| 症状・表示 | 確認すること |
|---|---|
| 解析・現像・書き出しが `SOURCE_ROOT_NOT_CONFIGURED` で止まる | 現像元フォルダを選んでいない。「フォルダを選ぶ」で選ぶ |
| 「写真が 0 枚」ではなく、許可を促すメッセージが出る | macOS のアクセス許可がない。「システム設定 > プライバシーとセキュリティ > ファイルとフォルダ」で許可して、フォルダを選び直す |
| 写真が 1 枚も解析されない | フォルダ直下に `DSC#####.JPG` / `.ARW` の同名ペアがあるか。サブフォルダ内、他の命名、RAW 単独は対象外 |
| `ARW_NOT_FOUND` | その撮影 ID の `.ARW` が現像元フォルダ直下にない（JPG だけのカットは現像できない） |
| `SIDECAR_NOT_FOUND` | 現像 CLI がない。`npm run build:coreimage` を実行する |
| `SIDECAR_TIMEOUT` | 現像が時間内に終わらなかった。もう一度実行する |
| `BUSY` | 現像・合成・候補生成が混み合っている。実行中の処理が終わってからやり直す |
| サムネイルが出ない | 画像は Tauri の asset プロトコル（スコープは `$APPDATA/coreimage/**` と `$APPDATA/thumbnails/**`）と、元の JPG は独自スキーム `geoframe://` で配信している。この配信か scope を疑う |
| 「写真」への登録がエラーになる | [4.7](#47-apple-写真への登録) のオートメーション許可を確認する |
| macOS を更新したら画が変わった | `apple_default` の内部パラメータは OS が決める値のため。[回帰確認手順](development/coreimage-regression-check.md) で確かめる |

旧版（Python 時代）の、リポジトリ内の `outputs/` や、アプリのデータフォルダの `logs/`・`drive_auth.json` が残っていることがありますが、現行のアプリは読み書きしません。

## 7. 開発者向け

### 7.1 テストと検証

```bash
npm test                 # フロント単体テスト（vitest。reducer など純粋関数）
npx tsc --noEmit         # 型検査
npm run build            # ビルド検証（vite build）
npm run lint
npm run build:coreimage && cargo test --manifest-path src-tauri/Cargo.toml   # Rust（解析・現像・合成・書き出し・候補生成）
swift test --package-path native/coreimage-cli                             # Swift（Core Image CLI）
```

`cargo test` は、`tauri-build` が同梱 CLI の存在をコンパイル時に検査するため、事前に `npm run build:coreimage` が要ります。各テストが何を押さえるかは [技術設計](DESIGN.md) の「テストの構成」にあります。

評価用の Python スクリプトのテストは、評価用の仮想環境で実行します。環境に入れるのは NumPy / Pillow / OpenCV だけ（`requirements-dev.txt`）で、rawpy・lensfunpy は要りません。

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m unittest discover -s tests -p 'test_*.py'
```

### 7.2 評価スクリプト

`scripts/` には、エンジン比較・候補生成のチューニング・回帰確認のための評価スクリプトがあります（`compare_engines.py`、`evaluate_candidates.py`、`evaluate_raw.py` など）。**アプリの実行には使いません。** モードと前提、使い分けは [評価経路](development/evaluation-paths.md) と各スクリプトの `--help` を参照してください。

旧エンジン（rawpy / `local_raw/`）で基準画像や候補を作り直す経路はアーカイブ扱いです。旧実装を含む最後の参照点はコミット `e838ecc` で、そのコミットを別の checkout で使います。

### 7.3 macOS 更新後の回帰確認

`apple_default` は OS が決める値のため、macOS を更新すると画が変わりえます。更新したあとは [回帰確認手順](development/coreimage-regression-check.md) で、実効パラメータの差分と画質指標を確かめます。最初の確認は次のスクリプトです。

```bash
npm run build:coreimage
scripts/coreimage-regression-applied.sh <ベースラインと同じ ARW のフォルダ>
```

### 7.4 WebView のデバッグ

debug ビルド（`tauri:dev`）で画面を右クリックし、「要素の詳細を表示」を選ぶと WebView の開発者ツールが開きます。WebView を自動操作するテスト（Playwright など）は持たないので、reducer は `vitest`、Rust と Swift は各単体テストで押さえています。

### 7.5 画面の手動確認の観点

UI に触れる変更では、次を目で確かめます（Tauri の `tauri:dev` か、ビルドした `.app` で行います）。

1. 起動直後（現像元フォルダ未設定／解析前／一覧）の表示が意図どおり。
2. フォルダ選択 → 解析の進捗 → 一覧（サムネイルが出る。出ないときは asset scope か `geoframe://` の配信を疑う）。
3. 操作パネル: 元の JPG、フィルムストリップ、原寸ビューア、←→ での移動、調整値を捨てるときの確認ダイアログ。
4. プレビュー → 本現像 → 前後比較。エラー時の文言（`SIDECAR_*` などの code がそのまま出る）。
5. ブラケットグループの合成（プレビュー／本合成）、現像候補の生成。
6. 書き出し → Finder で表示、「写真」アプリへの取り込み（初回はオートメーションの許可）。

### 7.6 EXIF と GPS の確認

原寸現像と本合成は、カメラのペア JPG の EXIF を引き継ぎます（Orientation は 1、寸法は更新、Software を設定、MakerNote は破棄）。**GPS は、ペア JPG にあればそのまま引き継ぎます。アプリが新たに GPS を書くことはしません**（[ADR 0003](adr/0003-python-removal-single-app.md) 決定 5）。引き継げなかったときも現像・合成は成功し、元の CLI の JPEG が残ります（EXIF なし）。

- 手元の確認: `mdls -name kMDItemLatitude -name kMDItemLongitude -name kMDItemOrientation <出力.jpg>`（Spotlight のメタデータ）。GPS 付きの実機の JPG ではまだ試しておらず、Spotlight の索引外の場所では値が出ないことがあります。`exiftool` は使っていません。
- 自動テスト: `cargo test`（`exif_inherit.rs` の合成 JPG で、GPS の保持と MakerNote の除去を確認）。

### 7.7 API 契約を変えるとき

フロントと Rust の契約（コマンド名・引数・戻り値・エラー code・`$APPDATA` 配下の保存先・EXIF/GPS の継承）は [API 契約](API_CONTRACT.md) が正です。コマンドを変えたら、同じ変更で契約も更新してください。
