# GeoFrame 写真選定・RAW現像支援機能 引継ぎ文書

作成日: 2026-08-06  
対象: GeoFrame（写真DB／スマートディスプレイ／旅行ブログ半自動生成）  
実装担当: Codex

## 1. 目的

旅行後に大量の写真を手作業で選別・現像する負担を減らす。

Sony α6400で撮影した **JPEG+ARWの同時記録**を前提とし、JPEGを高速な解析・比較に使い、価値がある写真に限って対応するARWを現像する。全RAWを一律にプレビュー生成・現像する必要はない。

実現したい主な機能は次のとおり。

1. JPEGとARWのペアリング
2. 連写・類似カットのグループ化と代表写真の推薦
3. 「RAW現像すると改善しそうな写真」の推薦
4. 露出ブラケットの検出とHDR合成候補の推薦
5. 星空写真の検出と、RAW現像・複数枚スタックの推薦
6. ユーザー承認後にだけ高品質処理を実行
7. 選定・処理結果を写真DBとブログ生成機能へ連携

完全自動で作品を決定する機能ではなく、**候補、理由、信頼度を提示して人が最終判断する半自動機能**とする。

## 2. ユーザーと撮影環境

- カメラ: Sony α6400
- RAW形式: Sony ARW
- 記録方式: RAW+JPEG
- 主なレンズ:
  - SIGMA 10-18mm F2.8 DC DN
  - SIGMA 30mm F1.4 DC DN
- 主な被写体:
  - 旅行・登山風景
  - 星空・星景
  - 高山植物などの接写
  - 犬猫
- 人物撮影は主目的ではない
- 広角写真を好む
- Nikon D80で得られた赤の発色や空の抜け感を好んでいたため、将来的にはユーザー固有の色プリセットも検討する

## 3. 基本方針

### 3.1 JPEGを解析用、ARWを仕上げ用にする

- サムネイル、類似判定、ブレ、構図、露出、被写体分類は原則JPEGで実行する。
- ARWはペアの存在確認とEXIF／メタデータ取得を行う。
- ユーザーが処理を承認した写真だけARWから現像する。
- JPEGがないARWについては、ARW内蔵プレビューを抽出するフォールバックを用意してよいがMVP必須ではない。

### 3.2 非破壊処理

- 元のJPEG／ARWは変更・削除しない。
- 推薦結果、採点値、ユーザー判断、現像設定はDBまたはサイドカーに保存する。
- 派生画像には元写真との関係と処理レシピを記録する。
- 同じ入力・レシピから再生成可能にする。

### 3.3 説明可能な推薦

「スコアが高い」だけでなく、以下のような理由を表示する。

- 同じ連写内で最もシャープ
- ハイライトの白飛びが少ない
- 星空、高ISO、暗部が多いためRAW現像の効果が大きい
- 同一構図で -2/0/+2 EV がありHDR候補
- 同一構図の星空が8枚ありノイズ低減スタック候補
- 木の葉や人物などの動体がありHDRゴーストの可能性あり

## 5. 処理パイプライン

```text
取り込み
  → メタデータ抽出
  → JPEG/ARWペアリング
  → 時刻と画像類似度で撮影グループ化
  → JPEGの品質・内容解析
  → ベストカット／RAW現像／HDR／星空スタック候補生成
  → UIで理由付き提案
  → ユーザー承認
  → 対応ARWのみ現像・合成
  → 派生画像とレシピをDB登録
  → ブログ生成候補へ連携
```

解析処理と重い現像・合成処理はジョブを分離する。写真取り込みを現像完了待ちでブロックしないこと。

## 6. ペアリングとグループ化

### 6.1 JPEG/ARWペアリング

基本キー:

- 同一ディレクトリまたは同一取り込みバッチ
- 拡張子を除いたファイル名が同じ
- 撮影時刻が一致または許容差内
- カメラのシリアル番号／機種が一致（取得可能な場合）

例:

- `DSC01234.JPG` ↔ `DSC01234.ARW`

ファイル名だけで衝突する可能性があるため、DB上の一意キーはファイル名にしない。ハッシュ、取り込みバッチID、撮影時刻などを併用する。

### 6.2 連写・類似カットのグループ化

候補条件:

- 撮影時刻差が短い（初期値1〜3秒、設定可能）
- perceptual hashまたは画像埋め込みが近い
- 焦点距離と画像サイズが同じ／近い
- 構図の特徴点が十分一致する

時刻だけでまとめるとカメラを振った写真まで混ざるため、視覚的類似度を必ず併用する。

HDRブラケットは露出値が異なるため、明るさに比較的頑健な特徴量または位置合わせ可能性でまとめる。

## 7. 代表写真の評価

### 7.1 客観指標

- シャープネス
  - Laplacian varianceだけで決めず、主被写体領域または複数領域を見る
- ブレ推定
  - エッジ方向、局所周波数、可能なら学習済みモデルを併用
- 露出
  - 白飛び率、黒つぶれ率、輝度分布
- ノイズ
  - ISOと平坦領域のノイズ推定
- 水平
  - 風景向けの補助指標。意図的な傾きもあるため減点は弱くする
- 構図
  - 主被写体の欠け、極端な余白、地平線位置など
- 被写体固有
  - 花: 花芯・主要な花への合焦
  - 犬猫: 目または顔への合焦、目つぶり
  - 星空: 星像の伸び、雲量、前景のブレ

### 7.2 スコア例

初期版はルールベースでよい。

```text
quality_score =
    0.35 * sharpness
  + 0.20 * blur_inverse
  + 0.15 * highlight_preservation
  + 0.10 * shadow_preservation
  + 0.10 * noise_inverse
  + 0.10 * composition
```

写真タイプにより重みを変更する。たとえば星空では水平より星像とノイズ、高山植物では画面全体より花の領域の合焦を重視する。

美的評価モデルは補助点として使ってよいが、客観指標を上書きさせない。モデル名、バージョン、推論設定を記録し、後で差し替え可能にする。

## 8. RAW現像推薦

### 8.1 推薦条件

- 星空または夜景と分類された
- ISOが高い
- シャドウ領域が広い
- ハイライトがJPEGで飽和している／飽和寸前
- 逆光または明暗差が大きい
- ホワイトバランス補正余地が大きい
- JPEGの強いコントラスト／彩度で階調が失われている可能性がある
- 良いカットだがJPEG品質上の問題がある

RAWの回復可能量を正確に判断するにはRAWデータの軽い統計解析が必要になる場合がある。MVPではJPEG+EXIFによる推薦でよく、必要に応じて上位候補だけARWを解析する二段階方式にする。

### 8.2 推薦レベル

- `none`: JPEGのまま採用可能
- `maybe`: 調整で改善する可能性あり
- `recommended`: RAW現像の効果が見込める
- `strong`: 星空、高ISO、強い逆光など、RAW処理を強く推奨

必ず理由コードと人間向け説明を保持する。

例:

```json
{
  "level": "strong",
  "confidence": 0.91,
  "reason_codes": ["NIGHT_SKY", "HIGH_ISO", "DEEP_SHADOWS"],
  "message": "星空・高ISOで暗部が多いため、RAW現像とノイズ低減の効果が期待できます。"
}
```

## 9. RAW現像

### 推奨構成

- メタデータ: ExifTool
- PythonからのRAW読み取り／簡易解析: rawpy（LibRaw）
- 最終現像候補: `darktable-cli` または RawTherapee CLI
- 画像処理: OpenCV、Pillow、NumPy

MVPでrawpy現像を採用してもよいが、レンズ補正、色管理、ノイズ低減、プリセット運用を考えると、最終品質にはdarktable CLI系が扱いやすい。既存環境とライセンスを確認して選定すること。

プリセット候補:

- `landscape_clear`: 登山・青空
- `alpine_flower`: 高山植物、赤や花色を重視
- `night_sky`: 星空
- `nightscape`: 夜景
- `pet_indoor`: 室内の犬猫
- `neutral_recovery`: 逆光・階調回復

プリセットは後で差し替え可能な外部設定として管理し、コードに数値を埋め込まない。

## 10. HDR候補と合成

### 10.1 候補検出

- 同一または近似構図
- 短時間内に撮影
- 露出値または露出補正値が段階的に異なる
- 典型例: `-2 EV / 0 EV / +2 EV`
- 2枚以上、通常は3枚以上

### 10.2 合成処理

1. RAWを同一ホワイトバランス・色空間で中間出力
2. 特徴点またはECCで位置合わせ
3. 動体領域を検出
4. ゴースト抑制
5. 露出融合またはHDR生成
6. 自然なトーンマッピング

OpenCVのMergeMertensは自然な露出融合の初期実装に使える。厳密なHDRや高品質なゴースト除去は別エンジンも比較する。

候補表示では「HDR向き」「位置合わせ可能」「動体あり」「三脚らしい」などを示す。葉、波、人、動物が動いている場合は警告し、自動処理を強行しない。

## 11. 星空処理

### 11.1 星空検出

EXIFと画像解析を組み合わせる。

- 夜間の撮影時刻（位置情報があれば日没・薄明も考慮）
- 長秒露光
- 高ISO
- 開放付近の絞り
- 暗い背景に多数の小さな高輝度点
- 星の並びがフレーム間で一貫して移動

街灯や夜景を星と誤認しないよう、単一条件で決めない。

### 11.2 単一RAW現像

- ホワイトバランス
- ハイライト保護
- シャドウ調整
- 色ノイズ／輝度ノイズ低減
- 適度なコントラスト・かすみ除去
- 星を過度に太らせないシャープ処理

### 11.3 複数枚スタック

同一構図の連続撮影がある場合に推薦する。

- 星基準の位置合わせ
- 地上基準の位置合わせ
- 星と前景を別処理して合成する選択肢
- sigma clipping等によるノイズ低減
- 飛行機、人工衛星、一時的な光跡の除外
- ダークフレームが特定できる場合は補正候補にする

星景は星と固定前景の動きが異なる。単純な全画面スタックだけで完成扱いにせず、前景のずれや境界を確認できるUIを用意する。

## 14. UI案

### グループ比較画面

- 類似写真を横並びまたは切り替え表示
- 推薦写真に印を付ける
- 各写真のピント位置拡大と白飛び警告を表示
- 「なぜ選んだか」を短文で表示
- 操作:
  - この写真を採用
  - 別の写真を採用
  - グループを分割／結合
  - RAW現像する
  - 全て保留

### 処理提案カード

表示例:

```text
連写代表候補: DSC01237
理由: 最もシャープで、白飛びが少ない

推奨処理: RAW星空現像 + 8枚スタック
理由: 同一構図の連続撮影、高ISO、星空を検出

[JPEGのまま採用] [RAW現像] [スタック作成] [別写真]
```

### ブログ連携

- 採用済み写真だけを記事候補として優先
- 同一グループから何枚も自動挿入しない
- 現像済み派生画像があればそれを優先
- 元写真、場所、日時、旅程イベントとの関連を維持
- AI生成記事の公開前には必ず人が確認する

## 16. 実装順序

### Phase 0: 既存コード調査

1. GeoFrameの写真取り込み、DB、サムネイル、ジョブ、ブログ機能を確認
2. 現在の写真IDと派生画像管理を把握
3. ARWが現在どのように保存・除外されているか確認
4. サンプル写真でEXIF取得状況を確認
5. 新規設計を既存の命名・構成に合わせる

### Phase 1: ペアリングと分析基盤

1. JPEG/ARWペアリング
2. EXIF正規化
3. 分析結果の保存
4. 冪等な再解析
5. CLIまたは管理APIで特定バッチを解析可能にする

### Phase 2: 連写グループと代表推薦

1. 時刻による候補グループ
2. pHash／特徴点による誤結合除去
3. 品質指標の計算
4. 代表候補と理由の生成
5. 最小限の比較UI

### Phase 3: RAW現像推薦・実行

1. シーン分類とRAW推薦ルール
2. 理由・信頼度表示
3. 承認後のジョブ実行
4. 派生画像、レシピ、失敗ログの保存
5. ブログ候補への反映

### Phase 4: HDR

1. ブラケット検出
2. JPEGで位置合わせ可能性を事前評価
3. RAW中間出力から合成
4. 動体警告・プレビュー比較

### Phase 5: 星空スタック

1. 星空グループ検出
2. 星基準スタック
3. 前景あり判定
4. 必要なら星／前景の分離処理
5. 除外フレームをユーザーが変更できるUI

## 17. 受け入れ条件

### Phase 1

- 同名JPEG/ARWが正しく1つの撮影として関連付けられる
- 同名ファイルが別フォルダにあっても誤って同一化されない
- 再取り込み・再解析で重複レコードが増えない
- 元ファイルを変更しない

### Phase 2

- 典型的な連写が同じグループになる
- 数秒以内でも明らかに異なる構図は分離される
- 各推薦に最低1つの具体的理由が表示される
- ユーザーが別写真を代表に変更でき、その判断が保存される

### Phase 3

- 星空、高ISO、逆光写真でRAW現像候補が生成される
- 通常の十分明るい写真を一律に推薦しない
- 承認されていないARWを自動現像しない
- 派生画像から元ARW、レシピ、エンジンバージョンを追跡できる
- 処理失敗時に元ファイルと既存派生画像を壊さない

### HDR／星空

- 露出ブラケットを通常の連写と区別できる
- 動体のあるHDR候補に警告が出る
- 星空スタックで入力フレームと除外フレームが分かる
- 処理前後を比較して採用／破棄できる

## 18. テスト用データセット

実写真は個人情報や位置情報を含む可能性があるため、公開リポジトリへ無断追加しない。

ローカルテストセットとして以下を用意する。

- 通常のJPEG+ARWペア
- 同名だが別日／別フォルダのペア
- 3〜10枚の連写（微ブレ、ピント差、白飛びを含む）
- 大きく構図を変えた近接時刻写真
- -2/0/+2 EVの三脚ブラケット
- 手持ちHDR候補
- 葉や人など動体のあるブラケット
- 星空1枚撮影
- 同一構図の星空8〜20枚
- 星景（固定前景あり）
- ダークフレーム候補
- 高山植物の接写

分析値の完全一致ではなく、グループと推薦順位が期待範囲に入るかをfixtureベースでテストする。

## 19. 運用・性能・安全性

- 新規取り込み時は低優先度のバックグラウンド解析にする
- 大量取り込みではバッチ単位で進捗表示する
- CPU／GPU／メモリ使用量に上限を設ける
- 現像・合成ジョブはキャンセル可能にする
- 中間ファイルは専用作業ディレクトリに置き、成功後に原子的に移動する
- 外部コマンドには配列形式で引数を渡し、ファイル名をシェル展開しない
- ARWやJPEGのパスを信頼せず、許可された写真ストレージ配下か検証する
- 失敗した中間ファイルの保存期間と清掃方針を決める
- GPSや撮影場所を外部AIへ送る場合は明示的な設定と同意を必要とする
- 画像をクラウドモデルへ送らなくても基本機能が動く構成を優先する

### 24.3 manifest.json と GeoFrame 側の取り込み

書き出しごとに `outputs/export/<バッチ名>/manifest.json` が生成される。GeoFrame本体へ取り込む際は、このファイルを入力とすれば元写真・現像条件・推薦結果をすべて復元できる。

主要フィールド:

- `items[].capture_id` — 元のファイル名（拡張子なし）。`photo_assets` との突き合わせキー
- `items[].variant` — `camera_jpg`（カメラJPEG採用）か `developed`（RAW現像結果）
- `items[].exported_file` — 同ディレクトリ内の実ファイル名
- `items[].source.jpg` / `.arw` / `.jpg_sha256` — 元ファイルのパスとハッシュ。同一性の検証に使う
- `items[].recipe` — §12 の `processing_recipes` 相当。調整値・レンズ補正・元ARWのSHA-256・エンジンバージョンを含み、再現現像が可能
- `items[].group` — グループID・種別・RAW推薦レベル・**推薦どおりか（`was_recommended`）**。§20 の学習データとしてそのまま使える
- `items[].exif` — 撮影日時・ISO・レンズ・焦点距離

取り込み手順は「manifest.json を読む → `capture_id` で既存アセットを引き当てる → `recipe` を `processing_recipes` へ、`group` を `capture_groups` へ写す → `exported_file` を派生画像として登録する」となる。元のJPG/ARWには一切書き込まないため、取り込みは何度でもやり直せる。

### 24.4 既知の限界

- **ブラケット検出が実データ未検証** — サンプル281枚に露出ブラケット撮影が含まれず（検出0件）、合成前提の§10も含めて実写真での確認ができていない。判定ロジック自体は合成データのテストで担保している。なおサンプルは96%の写真が非ゼロの露出補正値を持つため、判定は「2段階以上の異なる補正値 かつ 0.6EV以上の幅」を条件にしている。撮影間隔のしきい値を広げるとこの条件が偶発的に成立しうるため、しきい値変更時はブラケット件数の急増を確認すること。
- **同一バッチ名で再書き出しすると古いJPEGが残る** — `outputs/export/<バッチ名>/` は書き出し前に空にしていないため、前回の現像結果がフォルダに残り、Apple写真への登録対象にも含まれてしまう。バッチ名を変えるか、フォルダを手動で空にして回避する。
- **needs_review の定義** — グループ内で1位と2位の評価スコア差が小さい場合に立つフラグ。「代表選定の自信が低いので目視で確認してほしい」という意味であり、写真の品質が低いという意味ではない。グループ化のしきい値を広げてグループが大きくなるほど、候補が増えるため機械的に増加する。
- **グループ化しきい値は実データで調整済み** — `GROUP_GAP_SECONDS = 60.0` / `GROUP_FOCAL_RATIO = 1.5`（`local_raw/analysis.py`）。初期値12秒/1.3では85%が単写のままで統合が働かなかったため、「一つの場所に留まって数枚撮る」パターンが1グループにまとまる値へ広げた（単写84.6% → 57.6%、最大グループ6枚）。
- **焦点距離ルールはこのライブラリではほぼ発火しない** — 主力のSigma 10-18mmはズーム全域の比が1.8倍しかないため、`GROUP_FOCAL_RATIO` を1.8以上にするとルールが無効化される。現在の1.5は発火するが、別レンズを含む写真群では挙動が変わりうる未検証領域である。
- **RAW推薦しきい値は未調整** — 実データで45/158グループが候補となり妥当なため、初期値のまま。
- **サンプル依存** — `sample/100MSDCF` はこのマシン限定。CIでは実行せず、Python側テストはすべて合成データで動く。
